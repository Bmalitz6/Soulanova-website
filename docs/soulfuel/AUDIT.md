## Important concrete risks, without rebuilding features

1. **P0: verify the existing backend, not a new schema.** Four live endpoint names return permission-denied metadata under anonymous requests. Source policies alone do not prove deployed owner isolation. Stage tests with two dedicated test accounts; do not use member food records.
2. **P0: preserve account boundaries.** Keep published authentication intact. Add lifecycle clearing to the reused SoulFuel UI; isolate or explicitly migrate the mobile global diary before presenting it as account-backed storage.
3. **P1: prevent repeat writes and validate nutrient JSON server-side.** Manual double-submit duplication is reproduced. Sequential barcode protection exists; pending/racing requests and retries still need staging tests. Preserve the current per-consumed-portion semantics.
4. **P1: fix local-storage recovery before migration.** Mobile getItem has finally but no rejection handler; loaded can become true after failure and permit persistence of an empty array. Corrupt JSON/array rows are not schema-validated. Preserve the original key and data while implementing non-destructive recovery separately.
5. **P1: make history/unknown/goal behavior explicit.** Reuse existing daily history; add missing mobile date access and unknown-value handling additively. Do not advertise calculated recipe nutrition or universal food-database accuracy.

## Verification performed and limits

-18 positive functional fixture checks and1 reproduced-gap check: diary11 total,barcode8 total. Actual existing JS/HTML were loaded unchanged apart from replacing the external Supabase import with a fully in-memory client; all API reads/writes used synthetic data. No real Supabase auth/session or member writes. Detailed results: [diary](diary-fixture-tests.json),[barcode](barcode-fixture-tests.json).
-Read-only live checks requested **limit=0** for all four tables, returning401/42501. No member rows or write methods requested. SoulFuel/My Health production routes return404; the published600s Foundations route returns200. [Checks](readonly-live-checks.json).
-Mobile tsc --noEmit passed. Existing web SoulFuel/scanner/health modules pass Node module syntax checks. Lint could not run because package.json has no lint script and ESLint is not installed; no dependencies added.
-No new simulator build, real camera test, authenticated production test, schema introspection or RLS cross-account test was performed. Those are explicit verification gaps, not evidence that completed code is missing.

Supabase documents grants and RLS as separate controls; both must be verified for exposed objects ([official guide](https://supabase.com/docs/guides/api/securing-your-api),[RLS guide](https://supabase.com/docs/guides/database/postgres/row-level-security)). An anonymous permission denial is a useful bounded check, not certification of authenticated authorization.
